## 1. 从根因到改动

这次最重要的发现，是 Compass 不仅存在模型没有主动调用工具的问题，工具本身也制造了大量不必要的成本。

例如，PPTX 的 GPT-6 Luna Session 中，193 次顶层 `codemode` 调用包含约 876 次 Compass 工具调用表达式；Triage 被调用 77 次，其中 13 次因输入过长而失败。相同的多项状态查询脚本也被反复执行。

更严重的是，v0.3.1 的状态修改结果在已有持久化记录的情况下，仍然把完整 GoalRun 放进每次工具结果的 `details.state`。实际日志中，单次任务创建或状态更新的这部分数据就达到约 10–11 KB。

v0.4.0 针对这些问题做了以下修改。

## 2. 哪些最初的思想仍然保留？

这版没有偏离原来的架构方向。

- **DeepSeekHarness：** 继续复用 Pi 原生 `codemode` 和 Subagent，减少模型的机械操作；不自建第二套调度器。
- **Prove2Me：** 任务完成、Agent 报告通过、真实验收通过仍然是不同状态。
- **Messages：** 保留 Goal 版本、Human 指令和事件来源；通过紧凑投影与增量读取减少重复上下文。
- **Agent-first：** 工具 Schema、结果和异常路径围绕 Agent 的执行成本设计，不为了人类仪表盘增加额外结构。

这次没有加入自动 Fork 管理器、强制 DAG、自动回滚或通用验证器。我们还没有足够证据证明这些机制值得承担额外复杂度。

## 4. 安装与实测

先完整备份并替换原 V2 安装目录，不要只覆盖部分文件，也不要合并到 V1。

在 Compass 目录执行：

```bash
npm install
npm test
node scripts/preflight.mjs /path/to/target-project --require-compass
```

然后在 Pi 中执行：

```text
/reload
/compass-preflight
```

如果扩展入口导入、GoalRun 模块契约或动态工具注册检查失败，先停止实验。

接下来使用一个全新的 Session 完成真实 Goal。重点观察三个结果：

1. `compass_state` 是否确实替代了多次重复状态读取。
2. Triage 是否能够引用事件并避免重复诊断，而不是让 Agent 反复复制日志。
3. Goal、Human 指令和计划是否在 Compaction 及路线变更后保持一致。

**v0.4.0 的目标不是让 Agent 更频繁地调用 Compass，而是让它用更少的调用获得正确的状态和证据。** 这次我们已经针对日志中可直接确认的浪费做了修改；至于整体是否更快、更省，仍然需要下一轮真实执行数据来证明。
