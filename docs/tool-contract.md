# Compass tool contract — current development source

Compass tool content is Agent-facing JSON, selected explicitly rather than merged from private metadata. Persisted mutations return `resultStatus: applied|unchanged`, changed IDs and one cursor. Reads return domain data directly; there is no generic success/kind boilerplate or repeated prose summary. Context operations return queued first, then a correlated native applied/rejected receipt. Expected validation errors explain what did not change. Native `details` carries protocol state, not an accidental second Agent payload. Full caveats/evidence are retained in their on-demand reads. Mutation names are not repeated in payloads; the native tool call already supplies operation identity. Search provenance has one field, not duplicate `sources/provenance`. Triage records return applied/unchanged plus the new cursor, since recording a review changes Compass bookkeeping. A matching native tool-result is never removed to save bytes; complete call/result pairing remains mandatory. Automatic dispatch feedback is a field in the same owned JSON receipt, not appended prose that breaks programmatic decoding.

The tool surface is progressive. `compass_state` is the compact default read; use other tools only when current work needs them. The Agent chooses decomposition, attention and route; code validates deterministic state and safety boundaries. A frame or DAG is optional. Task completion and Agent-reported acceptance are not independent Goal verification.

## Goal state and work plans

- `compass_goal` explicitly records the Agent’s semantic objective, complete constraint list and optional acceptance criteria. `expectedVersion=0` creates the first Goal. `sourceIds` default to the latest native Human message; supplied sources must be Human records on this branch and include the latest input. Runtime validates identity/version, not the meaning of the interpretation. Raw prose never creates, changes or approves a Goal.
- Reaffirm the same objective and constraints after new Human input before resuming approved DAG progression. This preserves existing Human approval if the material definition is unchanged. Different objective text replaces Current Goal, increments its version and resets Goal-specific work; unresolved native run identities block replacement. Original Goal is the initial semantic interpretation, with original Human source references, not a duplicate transcript or Goal-change archive.
- `compass_state` returns a compact Goal/outcome/frame summary and only meaningful plan/acceptance information. It omits native inventory, repeated Goal events and empty diagnostics. Native tool diagnostics remain in `/compass-preflight`; Goal sources, constraints and answers are on demand in `compass_goal_read`; both reads expose `input.id/reviewed` when a native Human input has been observed. `reviewed=false` means the Agent has not reviewed that input, not that runtime has detected which constraint is semantically wrong or obsolete.
- Cursors include Goal revision, event sequence and native context revision (`R…-E…-C…`). Pass a previous cursor for bounded event deltas; omissions and retained-history gaps are explicit. Exact unchanged cursors return a small envelope with the committed `contextFrame` summary. `compass_history_recent` and `compass_triage` provide on-demand event evidence.
- `compass_open` offers optional capability groups after explicit Goal creation; the Agent chooses which to load. No Goal wording or write-count heuristic chooses planning or creates a DAG.
- `compass_plan_create` is optional. Tasks explicitly select `parent`, `code` or `subagent`; only read-only Subagent tasks can be auto-dispatched. `dispatchReason` must justify the extra semantic call. Code and parent tasks are not silently delegated.
- `compass_plan_status` reads readiness and stable task IDs. `compass_plan_revise` checks the current state version and unresolved execution state. `compass_task(action=...)` validates task identities, dependencies and lifecycle preconditions. Subagent tasks are started by Compass after eligible plan/task mutation boundaries; do not start them manually.
- `compass_execution(action=status|resolve)` is for failed or unresolved native batches. An unknown child must first be checked through native pi-subagents status; never infer it stopped or retry it automatically.

**Approval and progression contract:** A DAG is a draft until a correlated structured Human answer approves the exact Goal/criteria/tasks/dependencies/executors/constraints binding. Declined, partial, modified, stale and UI-error answers do not approve. Plan revision/constraint changes invalidate approval; task progression and auto-dispatch remain blocked until current approval. A completed task requires a separate explicit `assess` result with evidence; dependencies unlock only after a passing assessment with no unresolved caveats. Task completion, assessment, independent review and final Goal acceptance remain distinct. These code paths have local regression coverage; tests do not establish real Human UI or provider behavior.

## Same-session context frames

`compass_context_search({...})` is the read-only source-recovery entry point, callable in Code Mode without a preceding revision lookup. `compass_context({operation:{action,...}})` is model-only and operates on the current Pi session's context projection; it does not start a Pi session or Agent loop and does not roll back filesystem/environment effects. Mutation actions are `call`, `return`, `pin`, `unpin`, `transfer`, `replace`, `drop`, `load`, `move`, `spill` and `mark`. The native model-only exposure keeps them directly reachable in Code Mode-only mode and prevents nested invocation; no duplicate nested-call policy is maintained in a hook. Mutations are direct standalone calls, not nested Code Mode operations; the nested discriminated schema enforces required fields and rejects unrelated fields per action. The root remains an object for Pi/provider conversion. Search has no revision argument; `scope` is pin ownership, `sourceScope` is recovery, and watch transfer uses only `watchIds/watchScope`. Single-source moves require `version`; multi-source moves require per-source `versions`, and range moves cannot also coalesce a companion read. They bind the current revision/source versions and reuse the commit planner for early validation, then revalidate at the native turn boundary. Parent restoration metadata is reference-only and bounded by a 2 MiB canonical-control budget, independent of the 256-item selection bound. A 1,000-source frame does not require pre-compaction merely to pass a count ceiling. Context edits and parent restoration remain linear in the active source count, not free.

- In interactive Pi, the native footer shows `frame: root` or `frame <depth> · <id>`, derived from committed frame state without polling. `compass_state.contextFrame` exposes the same identity for programmatic feedback. No extra capacity query or polling call is required. The initial queued receipt contains only status, call ID, current revision and any created artifact path. It is not a committed frame; native terminal receipts correlate action/call ID and actual revision. The local task is retained on frame entry because its original tool exchange is omitted from the new attention frame.
- Frame capture/return is explicit and defaults to no captured or exported values. `ref` values are shared and survive interruption; `copy` values are private and fork on write. Complete tool-call/result exchanges are preserved.
- Search can find active, saved-parent and branch-history sources. Search/ranking expose original, retained and Agent/projection-derived authorship, native edit lineage, immutable read completeness and caveats. Loads/ranges are version checked. Binding identity is checked against the immutable native source/write record, not provenance; a derived value may cite different evidence sources. Move whole working values or selected Agent-text ranges; read-result ranges remain qualified data copies beside the complete original exchange. Candidate search is literal keyword recovery: default `match=any` ranks by distinct matched terms; explicit `match=all` requires every term in one text block. Complete recorded search-only tool envelopes are skipped in ordinary retrieval but remain recoverable by explicit ID. Search stays bounded at 1,024 candidates and 16 returned hits; output contains one snippet and matched terms, not a duplicate excerpt. `rankedSources` preserves the Agent's bounded semantic selection order while code verifies source IDs, versions and ranges; it is not a runtime semantic score.
- Pins are scoped retained context, not system-authority instructions. An exact successful, untruncated complete native Skill-file read must be explicitly pinned as `kind=skill`; loaded/copied/derived data cannot masquerade as that original read. `mark` tracks `active`, `handled` or `retired` status and retention lifetime. Before a semantic Goal exists, default pins/answers are session-scoped; explicitly requesting Goal-scoped retention requires a Goal.
- Spill writes and reads back a project-relative artifact before replacing context with a pointer. Linux descriptor-relative traversal prevents the reviewed ancestor-to-symlink redirection race; other platforms fail closed. It does not roll back filesystem effects; a rejected later native commit can leave a reported orphan artifact.
- Native pi-await watch identity/liveness is authoritative. A frame cannot return while it owns a live watch; use native unwatch or transfer the exact arm identity to an active parent/root scope. Repeating wakes are not terminal completion.
- The installed Pi 1.5.2 path can supplement an outgoing request with missing pinned context and materialize some changes at existing boundaries. This is not a guarantee of immediate canonical restoration after every compaction. Do not claim provider cache hits or live behavior from local projection/runner tests.

For repeated native reads, use `search(compare=[...])` and optionally `move(verifiedAgainst=...)`: exact repeats require persisted source path/range and payload identity, not bare text equality; a subset additionally requires a shared native file revision. Both covered result envelopes retain qualified pointers while one complete earlier payload/superset remains at the append end, with outside-subset lines durably qualified as unrefreshed. `verifiedAgainst` names the complete companion read; a selected comparison range cannot authorize removing its uncovered remainder. Pinned companions cannot be coalesced. Later changed or incomplete read evidence rejects verified relocation. Ambiguous paths stay unknown; similarity is advisory only. These operations are explicit/on demand, not a background optimizer; use them only when saved payload cost outweighs pointer/edit/cache costs.

## RouteSet

The optional routes capability exposes a persisted RouteSet separate from the DAG. Alternatives are not DAG siblings and are not automatically fanned out. Initial route choice uses the exact structured Human questionnaire, correlated through the persisted exchange, or an acceptance-gated result from already authorized exploration. `propose_exploration` prepares a new scope/budget/routes proposal; only its clear native Human answer authorizes it. Model-visible input cannot supply fabricated questionnaire results. Notes, partial/declined answers and UI errors withhold authorization. RouteSets contain 2–3 alternatives so their native questionnaire has at most four options. Competitor cancellation is exact-identity and acceptance-gated, with request/acknowledgement/terminal/unknown tracked separately. The RouteSet does not create branches or worktrees; filesystem/worktree coordination remains the Agent's responsibility. A selected route binds the DAG approval to its exact baseline/route; route changes invalidate prior task evidence and require fresh approval before execution.

Mutation receipts do not echo the whole RouteSet, submitted criterion bodies or an old questionnaire. They return current stateVersion/selection/winner and the affected run identity/status/gate, including unresolved criterion IDs and material caveats. Only create/propose returns the generated questionnaire. `status` remains the on-demand full evidence read.

## Native Subagents and waits

Compass delegates eligible read-only child tasks through the documented pi-subagents Structured Delegation API. It does not force-enable native tools or alter the user's tool preferences. pi-subagents owns child execution/status/cancellation; pi-await owns watch lifecycle/wakes. Compass correlates receipts and consumes child feedback but does not claim child success as Goal acceptance. Recursive Compass use inside children is not supported by the installed launch contract.

## Acceptance

`compass_acceptance_status`, `compass_acceptance_define` and `compass_acceptance_record` manage Goal criteria separately from DAG task status. Definition receipts return current IDs/statuses; status reads return complete current criterion text/evidence without prose clipping or duplicated summaries. Duplicate/over-limit definitions and over-limit evidence fail before mutation rather than silently truncating. Goal replacement reports reset counts; it never promotes old criterion reports into a new Goal. This does not mandate when the Agent defines or records acceptance. A task marked done or an Agent-reported pass is not independent verification. Missing, stale, partial or contradictory evidence remains unknown/inconclusive.
