# Pi Compass V2 v0.7.0 — Root-cause analysis and design decisions

## Executive decision

The next improvement is not another general-purpose workflow layer. It is a smaller, more exact execution surface: deterministic code controls state legality and tool visibility; semantic tools are exposed only when a narrow, observable condition makes them plausible; project conventions are not duplicated into a runtime-owned registry; measurement distinguishes model/transport failures from tool failures.

This preserves the project contract: **lower total cost to complete arbitrary Goals without lowering delivery quality**. More Compass calls, forced DAGs, and mandatory validation steps are not success criteria.

## Root causes and v0.7.0 changes

### 1. Native semantic delegation was always visible

**Problem:** v0.6.0 preserved native Subagent visibility regardless of task state. That avoids hiding a useful tool, but it leaves the model free to choose semantic delegation even when the task is a single deterministic route. This contradicts the code-first principle and creates an unnecessary choice in the tool surface.

**Change:** native Subagent tools are hidden unless either:

- the current DAG contains at least two tasks that remain pending, are ready, declared read-only, and have all prerequisites satisfied; or
- Human explicitly requests Subagent use or parallel scouting across multiple independent paths.

The gate is reversible. An explicit Human prohibition overrides DAG eligibility. When Human changes their instruction, the latest explicit request or prohibition takes precedence over earlier directives. Already in-progress tasks are not treated as fresh delegation candidates. It does not create a DAG, automatically spawn agents, or claim delegation is cheaper. Pi/user-disabled Subagent tools are not force-enabled. The second condition preserves the valid case where Human explicitly wants parallel scouting before creating a DAG.

**Boundary:** the gate determines eligibility from structured state and explicit Human intent; it cannot prove in advance that a semantic subagent will outperform deterministic inspection. It deliberately does not introduce a second scheduler.

### 2. `compass_open` exposed capability choices even when they were irrelevant

**Problem:** the old loader schema always offered planning, goal details, history, and acceptance. That increases the model's choice space and makes simple Goals look like they need a framework workflow.

**Change:** capability availability is derived from current Goal/state. A simple Goal has `compass_state` but no active `compass_open`. The loader schema lists only currently applicable and not-yet-loaded groups. It is hidden when nothing relevant remains unopened, preventing no-op opens and the resulting model/tool overhead. Planning uses explicit multi-stage/workstream intent, at least two actionable numbered items, or the existing three-distinct-write-target fallback. A numbered diagnostic/evidence list alone is not enough. Acceptance, history, details, issue review, and Goal change are exposed only when current state or explicit intent makes them relevant.

**Boundary:** this is intentionally a conservative deterministic signal, not a natural-language compiler. If a complex Goal has no explicit planning signal, the Agent can ask Human to clarify/plan; the existing write-target fallback is still available. The signal only exposes tools; it never creates a DAG automatically.

### 3. Compass duplicated user conventions

**Problem:** a separate persistent conventions registry and context injection created a second source of truth beside project `AGENTS.md` and the Human's own local conventions. The TTS Goal itself contains a `conventions:` section (`rg` over `grep`, `fd` over `find`, `amend` over Python heredoc replacement). Copying these as pinned runtime directives duplicates information and encourages a large hard-coded convention compiler.

**Change:** remove convention CRUD tools, registry reads/writes, and duplicate context injection. Labelled `conventions`/`preferences` sections are kept in the Goal source but are not copied into the runtime directive ledger. Explicit `Restrictions`/`Constraints` remain structured for Messages continuity. Any old user-side conventions file is left untouched and is no longer read or injected.

**Boundary:** this does not remove current-Goal Human constraints, Goal-versioned decisions, failure history, or checkpoints. Messages continuity is still required; global conventions ownership is not.

### 4. Measurement hid model request failures and mishandled numeric timestamps

**Problem:** the old report focused on `toolResult.isError`, missing failed assistant requests that can wait for minutes without producing a tool call. Numeric Unix-millisecond timestamps were not parsed reliably, so session elapsed-time calculations could be missing or wrong.

**Change:** `session-report.mjs` now counts assistant/model request errors separately, breaks them down by provider/model, and records reported duration, transport phase, and request bytes where available. It normalizes Unix milliseconds, Unix seconds, and ISO timestamps.

**Result from the new analyzer:** 50 model request errors are visible, including the 42 transport timeouts above. This prevents attributing infrastructure failures to Compass without evidence.

## Why not add more runtime semantics?

The code/semantic boundary is now explicit:

- **Code:** schema validity, tool availability, current Goal/version, task readiness/dependencies, no-op detection, cursor consistency, native Subagent eligibility, and metrics.
- **Semantic model:** interpreting a Goal, naming workstreams, deciding whether an available semantic investigation is worth the cost, and writing acceptance language.
- **Human / `AGENTS.md`:** local conventions and preferences. Compass should not maintain a second convention store or encode every preference into runtime policy.

A deterministic gate can narrow the choice set, but it should not try to replace semantic understanding with hundreds of brittle keyword rules. That would recreate the V1 problem in a different form.

## Regression coverage

- Simple Goal: only `compass_state`; no capability loader and no native Subagent visibility.
- Explicit multi-stage Goal: planning tools appear without auto-creating a DAG.
- Diagnostic numbered headings and quoted examples: do not activate planning.
- Two ready read-only DAG tasks: native Subagents become visible.
- After the candidate count drops below two (including when a task starts): Subagents are hidden again. Explicit Human prohibition overrides DAG eligibility; later explicit instructions supersede older ones.
- Explicit Human parallel scouting across multiple independent paths: Subagents can be visible before a DAG, but no DAG is auto-created.
- Native Subagent disabled by the user before load or while visible: Compass does not force-enable it.
- Convention registry absent; labelled conventions are not duplicated into session directives, while explicit hard restrictions remain. Fenced examples and trailing unheaded instructions must not be swallowed by the convention section detector.
- Numeric timestamp parsing and assistant-request error reporting have regression tests.

## Known limitations / user-side evidence still needed

1. The build container has no Pi CLI. Real Pi 1.3.0 dynamic tool activation/schema replacement is not verified here.
2. The four supplied traces do not encode a reliable package hash; they are a retrospective operational baseline, not a clean A/B benchmark.
3. Subagent visibility is gated, not automatically dispatched. If the tool is already hidden by Compass, Pi's active-tool API may not reveal a later user attempt to disable that already-inactive tool.
4. The current planning signal is intentionally narrow. It may miss a complex Goal that does not explicitly describe its stages and has not yet produced three distinct write targets.
5. `agent_reported_satisfied` remains a report state, not independent verification. Human quality review and external evidence remain necessary where the Goal requires them.
